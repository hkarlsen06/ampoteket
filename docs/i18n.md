# Localization

The site is published in Norwegian (bokmål, default) and English. Norwegian is the
source language: a string is written there first. Implementation:
`src/lib/i18n/`, `src/params.ts`, `src/hooks.server.ts`,
`src/routes/[[locale=locale]]/`.

## 1. How it works

**The URL decides the language.** Norwegian has no prefix; English sits behind `/en`
(`/p/AMP-00123` vs `/en/p/AMP-00123`). Nothing sniffs `Accept-Language` and nothing
redirects, so one URL is always one language and printed QR labels
(`ampoteket.no/p/AMP-00123`) stay valid forever. `/nb/...` is deliberately a 404.
API routes (`/api/...`) live outside `src/routes/[[locale=locale]]/` so they are not
duplicated under `/en`.

The moving parts:

1. `src/lib/i18n/nb.ts`: the Norwegian dictionary; `typeof nb` is the `Messages` type.
2. `src/lib/i18n/en.ts`: `export const en: Messages`. A missing, extra or misshapen
   key is a **compile error**, so `bun run check` is the completeness test. There is
   no runtime fallback.
3. `src/lib/i18n/locales.ts`: the locale list (import-free, because the build loads it
   through `src/params.ts` in plain Node). `src/lib/i18n/index.ts` re-exports it and holds the URL helpers (`localizeHref`,
   `stripLocale`, `localeFromPathname`) and the context (`setI18n`, `getI18n`).
4. `src/routes/[[locale=locale]]/`: every page. `+layout.ts` turns the optional
   parameter into a locale; `+layout.svelte` puts `{ locale, m, href }` into context.
   The `locale` matcher in `src/params.ts` matches only real prefixed locales, so `/p` is not a language.

`<html lang>` is set per request in `hooks.server.ts` and re-synced by the layout
after client-side navigation. The layout emits `hreflang` alternates for every
locale plus `x-default`.

The language picker is two ordinary links in the header menu, server-rendered
(`Collapsible.Content forceMount`), so it works without JavaScript. It keeps public
query strings such as catalog filters. On checkout/admin pages it keeps only the
localized path, never Auth callback material; those private routes also omit
canonical, alternate and social URL metadata and use noindex/no-referrer.
`static/robots.txt` blocks nothing, so crawlers can read that noindex, and points
to `static/sitemap.xml`, which lists the indexable pages in both locales; add a
page there when it becomes public.

There is no i18n library on purpose: two typed dictionaries and one context are
enough. Revisit only if plurals in many languages, gendered forms or translator
tooling become necessary.

## 2. Using it in a component

```svelte
<script lang="ts">
	import { getI18n } from '#lib/i18n/index.js';

	const i18n = getI18n();
	const m = $derived(i18n.m.home);
</script>

<h1>{m.hero.title}</h1>
<a href={i18n.href('/p')}>{m.hero.parts}</a>
```

- Read `i18n.m` through `$derived` so it follows navigation.
- No user-visible text in components, including accessible names: pass localized
  labels to icon buttons, slider thumbs and dialog close controls.
- **Every internal link goes through `i18n.href(path)`**, written unprefixed. A raw
  `href="/p"` silently drops an English visitor into Norwegian. `bun run lint`
  rejects hard-coded internal paths in `href`, `goto()`, `pushState()` and `replaceState()`.
- `page.url.pathname` contains the prefix; use `stripLocale()` before comparing.

## 3. Adding a string

1. Add the key to `src/lib/i18n/nb.ts`, in the section for the page that uses it.
2. Run `bun run check`. It fails, pointing at `en.ts`.
3. Add the English text. Run it again.

When a string needs a value, make it a function
(`cartLines: (n: number) => \`, ${n} linjer i handlekurven\``); every language then
gets the same arguments. Never concatenate sentence fragments in components.

Norwegian compounds can be wider than a phone. Put a soft hyphen (`­`) in long
display words when a 360 px check shows it is needed.

## 4. Editing both languages side by side

`bun run i18n` starts a local editor (port **5175**, ctrl+c to stop) that lists every
string with Norwegian and English side by side, filterable by key or text, and saves
straight back into the dictionaries. It is a development tool in `scripts/`, never
part of the deployed site. Run `bun run check` after editing.

- It rewrites **only the string literals you changed**; comments, formatting and
  untouched strings stay byte-identical.
- It does **not** add, delete or reorder keys; adding a key is still §3.
- It re-reads the files on every save but cannot see an unsaved buffer in your
  editor: do not edit the same dictionary in both places at once.
- **It has no login and writes to `src/lib/i18n/`.** Three safeguards must stay:
  it binds `127.0.0.1` unless `HOST=` overrides it; it rejects any `Host` header not
  in its allowlist (`localhost`, `127.0.0.1`, `[::1]`, `*.ts.net`, plus any names in
  `ALLOWED_HOSTS`), which stops DNS rebinding; and `POST /api/save` requires an
  allowlisted `Origin`. Exposed beyond the machine, it must stay on a private network
  (VPN or tailnet), never the public internet. `PORT=` moves the port.

To use it from another machine, start it with `HOST=<private address>` and list the
name you browse to in `ALLOWED_HOSTS=a.example,b.example` (for example a reverse
proxy in front of it on your private network).

## 5. Adding a language

1. Copy `en.ts` to e.g. `de.ts`, translate, keep `: Messages`.
2. Add the code to `locales` in `locales.ts`, and to `htmlLang`, `ogLocale` and
   `dictionaries` in `index.ts`.
3. Run `bun run check`, then verify the new route, the picker and the link-preview
   locale. The route matcher, `hreflang` links and `i18n.href()` follow the locale list.

The first entry of `locales` is the unprefixed default. Changing it changes every
existing URL, so do not. Product names exist only in Norwegian and English columns;
other languages fall back to the English name.

## 6. What is not translated

- **Product names** are stored in both languages (`name_nb`, `name_en`) and shown
  per locale via `productName()` in `src/lib/catalog.ts`. Electrical measurements in
  names and numeric specifications display with SI prefixes and the locale's decimal
  separator; stored values are unchanged. Search matches both languages.
- **Descriptions and other database content** are stored once, in the language the
  admins typed, and shown as is.
- **Codes, prices and quantities** are language-independent. Dates in copy are
  written out per language.
- **Categories:** standard categories have display labels in each dictionary's
  `categories` section. `categoryLabel()` matches the saved name ignoring case and
  surrounding whitespace (`Resistors` → «Motstand» / “Resistor”); unknown names show
  as saved. Labels are display only: API data, illustrations, filter values and query
  strings keep the stored name. Search matches both labels and the stored name. Add a
  standard category by extending the mapping and both dictionaries together (the admin
  list is in [page-admin-stock.md](page-admin-stock.md#products)).
- **Specifications:** standard fields in `src/lib/product-specifications.ts` have
  labels in both dictionaries, used when a recorded definition matches the standard
  code, type and canonical unit. Custom definitions keep their saved labels. Keep the
  field mapping and both dictionaries in sync.
- **Units** display through `unitLabel()` in `src/lib/format.ts`: `pcs` reads «stk»
  in Norwegian and “piece”/“pieces” (standalone “pcs”) in English; other units show
  their code. Money uses `currency()`: «kr» / “NOK”.
